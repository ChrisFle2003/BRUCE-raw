# Cockpit V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the optional static Cockpit-Mod as a local browser interface
that starts existing BRUCE CLI runs, records them under `runs/cockpit/`, and
keeps bundle, replay, and gate semantics in the existing CLI.

**Architecture:** `bruce cockpit [--port N]` starts a loopback-only HTTP
server and prints its URL without opening a browser. The server serves a small
same-origin browser UI and delegates every accepted job to the exact BRUCE
binary that launched it; a local job store and POSIX child-process adapter
provide logs, cancellation, controlled parallelism and reconnection during the
same server lifetime.

**Tech Stack:** C++20, CMake 3.20+, CTest, Python 3 integration tests,
POSIX `fork`/`execv`/`waitpid`/pipes, and vendored `cpp-httplib` v0.59.0
(MIT, header-only; HTTP only).

**Spec:** [Cockpit-Mod V1 – Architekturdesign](../specs/2026-10-04-cockpit-v1-design.md)

## Global Constraints

- Build Cockpit only as the static target `bruce_mod_cockpit`, controlled by
  `BRUCE_BUILD_MOD_COCKPIT`; no dynamic plugins or reverse Core dependency.
- Bind only `127.0.0.1`; no LAN/Internet binding, TLS, external API, telemetry,
  browser auto-open or Build-time network access.
- Use the launching BRUCE executable path directly as the child program; never
  invoke a shell or resolve a command through `PATH`.
- Create all new Cockpit files only below `runs/cockpit/<job-id>/`; reject
  Cockpit-created output and store paths outside the canonical job directory.
- Imported existing `.bruce` files are explicit, read-only inputs. Do not copy,
  move, delete or alter them.
- Start with one active job. Higher parallelism requires a visible, per-start
  choice and still uses independent child processes.
- Replay and gate are explicit job actions, except an explicitly selected
  existing `--verification replay`; no hidden follow-up execution.
- Do not treat UI labels, job metadata or technical Mod output as mathematical
  evidence, proof, gate success or rule authority.
- Update `docs/cli/source-index.md`, `docs/cli/examples.json` and
  `docs/cli/validation.md` only by running `docs/cli/verify_examples.py` in a
  temporary native copy, never by hand.
- Execute the existing wrapper only from a native project path without `:`;
  validate a GVFS checkout through a full temporary native copy instead.

## Review Focus

- A port already owned by another local process must fail; it must not silently
  share the port or bind a different address. **Task 4 integration test.**
- A raw expert request containing shell syntax, a NUL byte, a foreign program
  or `--output` outside `artifacts/` must create no child and no file.
  **Task 2 unit and Task 5 HTTP tests.**
- A browser refresh while a child runs must show the same job, accumulated logs
  and state; a server restart must show the documented unresolved state rather
  than claiming live reattachment. **Task 3 unit and Task 5 integration tests.**
- A SIGINT cancellation must preserve the child’s own exit/result semantics and
  never synthesize a replay, gate or scientific status. **Task 3 process test.**
- An imported external `.bruce` file must retain an identical SHA-256 before
  and after explicit inspect, assess, replay and gate jobs. **Task 5 integration
  test.**

### Task 3: Add the POSIX child-process and cancellation adapter

**Files:**

- [ ] **Step 2: Run the process cases and verify failure.**

  Run: `ctest --test-dir <native-build> -R cockpit_contracts --output-on-failure`

  Expected: child lifecycle assertions fail until pipes, `fork`/`execv`,

- [ ] **Step 3: Implement the process adapter.**

  Use POSIX pipes, `fork`, `execv` and `waitpid`; pass the prevalidated vector

  persisted `RUNNING` entries `UNRESOLVED_AFTER_SERVER_EXIT` rather than
  claiming to reattach them.
