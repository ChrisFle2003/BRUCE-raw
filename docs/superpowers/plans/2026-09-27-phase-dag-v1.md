# PhaseDagV1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Einen kleinen, seriellen und vollständig replaybaren Phase-DAG-Referenzkern mit festen Testadaptern liefern.

**Architecture:** Der neue Kern lebt ausschließlich unter `bruce/phase_dag`, besitzt eigene Spec-, Receipt-, Trace- und Bundletypen und verändert keine bestehende Application-Ausführung. Zuerst validiert er eine kanonische DAG, dann führt er exakt einen intern registrierten Fixture-Adapter nach dem anderen aus und schließlich bestätigt Replay jedes Receipt durch erneute, deterministische Ausführung.

**Tech Stack:** C++20, STL, bestehendes OpenSSL-SHA-256 über `bruce::sha256`, CMake, Ninja und CTest.

**Spec:** `docs/superpowers/specs/2026-09-27-phase-dag-v1-design.md`

## Global Constraints

- Die DAG-Version ist exakt `phase-dag-v1`; Bundleheader ist exakt `BRUCE_PHASE_DAG_RUN_V1`.
- Node-, Adapter- und DAG-IDs sind 1..64 ASCII-Zeichen aus `[A-Za-z0-9_.-]`; Node-IDs und Abhängigkeitslisten sind byteweise ASCII-sortiert und eindeutig.
- Eine Spec hat 1..16 Nodes, höchstens 15 Abhängigkeiten je Node, höchstens 64 Kanten, `max_started_nodes` 0..16, `max_receipt_bytes` 1..262144 und `max_trace_entries` 2..512.
- Die V1-Ausführung ist seriell und azyklisch. Ein Zyklus, eine Selbstkante, doppelte/unsortierte Abhängigkeiten, unsortierte Nodes, unbekannte IDs oder ungültige Requestdigests sind Fehler vor jedem Adapteraufruf.
- Ein Adapter erhält nur unveränderliche Requestbytes und kanonisch sortierte `PhaseInputRefV1`; versteckte Dateisystem-, Netzwerk- oder globale Eingaben sind unzulässig.
- V1 registriert ausschließlich interne Fixture-Adapter. Keine dynamischen Plugins, kein NanoCell-Adapter, keine ApplicationTask-, ExecutionSession-, CLI-, Gate-, Language-, Experience-, GPU-, Parallel- oder DAG-zu-DAG-Integration.
- `READY` ist ein Scheduler-Receipt und kann einen Adapteroutput `COMPLETE`, `INCOMPLETE` oder `REJECTED` enthalten. Kein Adapter- oder DAG-Status stärkt einen fachlichen Claim oder öffnet Learn-/Publish-Gates.
- Ein globaler Control- oder Budgetstopp hat Vorrang: noch unentschiedene Nodes werden `CANCELLED`; ohne globalen Stopp führt ein nicht-`READY`-Vorgänger zu `BLOCKED` ohne Adapteraufruf.
- Bundlewerte verwenden rohe ASCII-Length-Prefix-Felder `decimal-length ':' bytes` ohne führende Null; Request-, Receipt- und äußere SHA-256-Digests sind Prüfintegrität, keine Authentifizierung.
- Das Arbeitsverzeichnis ist kein Git-Repository. Keine Commit-/Branch-Operationen; Tests ausschließlich aus vollständigen, frischen `/tmp`-Release-Kopien und Befunde dateibasiert festhalten.
- Keine Paketinstallation, keine Netzwerkzugriffe und keine destruktiven Befehle.

## Review Focus

- **Nichtkanonische Graphrepräsentation:** Sortierte, aber semantisch gleiche Nodes/Edges dürfen nicht in mehreren Byteformen akzeptiert werden; Task 1 testet Node- und Dependency-Reihenfolge, Duplikate, Selbstkanten und Zyklen vor jedem Fixture-Aufruf.
- **Schedulerstatus versus Adapterstatus:** Ein `INCOMPLETE`-/`REJECTED`-Output muss `READY` bleiben und an einen zulässigen Join weitergegeben werden; Task 2 prüft diese Trennung explizit.
- **Stopppriorität:** Globales Budget oder Cancellation darf nicht teils `BLOCKED`, teils `CANCELLED` markieren; Task 2 prüft Control vor Start und Budget mitten im kanonischen Ablauf.
- **Receiptgrößenfehler nach Adapterausgabe:** Ein zu großer Output/Evidence-Receipt darf keinen partiellen `READY`-Output exponieren; Task 2 testet die Fehler-/Folgeverarbeitung.
- **Neu gehashte Bundlemanipulation:** Erneuerte äußere Prüfsummen dürfen falsche Inputs, Receipts, Status, Reihenfolge oder Evidenz nicht legitimieren; Task 3 prüft jede dieser Klassen.

  ```cpp
  namespace bruce {
  struct PhaseNodeSpecV1 { std::string node_id, adapter_id, adapter_version; std::vector<std::string> dependencies; std::string request_bytes, request_digest; };
  struct PhaseDagSpecV1 { std::string dag_version{"phase-dag-v1"}, dag_id; std::vector<PhaseNodeSpecV1> nodes; std::uint64_t max_started_nodes{}, max_receipt_bytes{}, max_trace_entries{}; };
  struct PhaseInputRefV1 { std::string producer_node_id, producer_adapter_id, producer_adapter_version, producer_status, producer_output_digest, producer_evidence_digest; };
  enum class PhaseOutputStatusV1 { complete, incomplete, rejected };
  struct PhaseOutputRefV1 { std::string output_version{"phase-output-v1"}; PhaseOutputStatusV1 status; std::string output_bytes, output_digest, evidence_bytes, evidence_digest, claim_scope; };
  enum class PhaseReceiptOutcomeV1 { ready, blocked, failed, cancelled };
  struct PhaseReceiptV1 { std::string node_id, adapter_id, adapter_version, request_digest; std::vector<PhaseInputRefV1> input_refs; PhaseReceiptOutcomeV1 outcome; std::optional<PhaseOutputRefV1> output; std::string failure_code; };
  enum class PhaseTraceEventV1 { validated, started, ready, blocked, failed, cancelled, completed };
  struct PhaseTraceEntryV1 { PhaseTraceEventV1 event; std::string node_id; };
  void validate_phase_dag_spec_v1(const PhaseDagSpecV1& spec);
  }
  ```

### Task 2: Serieller Fixture-Scheduler, Receipts und Stoppsemantik

**Files:**
- Modify: `include/bruce/phase_dag/phase_dag.hpp`
- Modify: `src/phase_dag/phase_dag.cpp`
- Modify: `tests/unit/phase_dag_tests.cpp`

**Interfaces:**
- Consumes: alle Task-1-Typen und `validate_phase_dag_spec_v1`.
- Produces:

  ```cpp
  namespace bruce {
  struct PhaseDagControlV1 { std::function<bool()> cancelled; };
  struct PhaseDagRunV1 { PhaseDagSpecV1 spec; std::vector<PhaseReceiptV1> receipts; std::vector<PhaseTraceEntryV1> trace; };
  PhaseDagRunV1 execute_phase_dag_v1(const PhaseDagSpecV1& spec, const PhaseDagControlV1& control = {});
  }
  ```

- [ ] **Step 1: Schreibe die fehlschlagenden Schedulerfälle**

  Definiere ausschließlich diese internen Fixture-Adapter im Testvertrag:

  - `fixture-source-v1`: Request `C:<bytes>`, `I:<bytes>` oder `R:<bytes>` erzeugt den zugehörigen Outputstatus und exakt die Bytes hinter dem Präfix; Request `F` wirft `FixtureFailure`.
  - `fixture-join-v1`: leerer Request, mindestens ein Input; Outputbytes sind die kanonische ASCII-Length-Prefix-Verkettung der Vorgängeroutputbytes in Input-ID-Reihenfolge, Status `COMPLETE`.

  Prüfe zwei Quellen `a`, `b` und Join `c`: Startfolge `a,b,c`; Join-Inputrefs sind `a,b`; drei `READY`-Receipts und korrektes `VALIDATED ... COMPLETED`-Trace. Prüfe außerdem, dass `I:x` oder `R:x` trotzdem `READY` ist und ein Join den Outputstatus als Input-Ref erhält.

- [ ] **Step 2: Ergänze Rotfälle für Abhängigkeiten und globale Stopps**

  Teste eine fehlgeschlagene Quelle `a`, abhängiges `b` und unabhängiges `c`: `a=FAILED`, `b=BLOCKED`, `c=READY`. Teste `max_started_nodes==0` und einen Controlcallback vor `b`: der aktuell und alle später unentschiedenen Knoten sind `CANCELLED`, nicht `BLOCKED`; keine weiteren Fixture-Aufrufe. Teste eine kleiner als die tatsächlich entstehende Receiptliste gesetzte `max_receipt_bytes`: Der verursachende Knoten wird `FAILED` mit `DagReceiptBudgetExceeded`, gibt keinen Output frei und abhängige Knoten werden `BLOCKED`.

  Run: `ctest --test-dir <build> -R '^phase_dag_contracts$' --output-on-failure`.

  Expected: FAIL, weil `execute_phase_dag_v1` fehlt.

- [ ] **Step 3: Implementiere den privaten Fixture-Adapterdispatcher und `execute_phase_dag_v1`**

  Halte die Adapterregistrierung als privaten, geschlossenen Switch über genau `fixture-source-v1` und `fixture-join-v1`; unbekannte Adapter führen zu `FAILED` mit `UnknownPhaseAdapter`. Erzeuge eine tiefe, unveränderliche Spec-Kopie vor jedem Callback. Starte nur den kanonisch kleinsten entscheidungsfähigen Node. Adapterausnahmen werden `FAILED`; nichtglobale Fehler blockieren nur Nachfolger. Ein zu großer resultierender Receipt wird in `FAILED/DagReceiptBudgetExceeded` zurückgestuft, ohne dessen Output/Evidence auszugeben. Halte `INCOMPLETE`/`REJECTED` strikt im `PhaseOutputRefV1` und nie im Receipt-Outcomefeld.

- [ ] **Step 4: Prüfe Scheduler und Rückfallregeln grün**

  Run: `ctest --test-dir <build> -R '^phase_dag_contracts$' --output-on-failure`.

  Expected: PASS; jeder Node erhält genau ein Receipt, globale Stopps haben Vorrang und unabhängige Arbeit bleibt bei lokalem Fehler möglich.

- [ ] **Step 2: Belege den roten Bundle-Test**

  Run: `ctest --test-dir <build> -R '^phase_dag_contracts$' --output-on-failure`.

- [ ] **Step 3: Implementiere `pack_phase_dag_run_v1` und `replay_phase_dag_run_v1`**

  Verwende ausschließlich private, begrenzte ASCII-Length-Prefix-Codecs. Pack vergleicht zuerst den übergebenen Run mit einer frischen Ausführung ohne Control. Der Body enthält genau canonical-Spec-Bytes plus Digest, canonical-Receipt-Bytes plus Digest und canonical-Trace-Bytes; Header und äußerer Digest rahmen ihn. Replay prüft Framing und Grenzen, rekonstruiert die Spec, führt sie ohne Control erneut aus, vergleicht jedes Receipt und jeden Traceeintrag und verlangt abschließend byteidentisches Repacken. Der Codec darf keine Datei schreiben und keine NanoCell- oder Application-Bundles interpretieren.
